# Выгрузка Discord через Vencord

Выбраны только `1317165120128028773` и `1525821262054817842`. Их ID записаны в `cloud/config/discord-guilds.json` и в настройках плагина. Переменная DISCORD_GUILD_IDS может явно заменить список; пустая строка отключает все серверы.

## Подключение

1. Для собственного плагина нужна сборка Vencord из исходников: https://docs.vencord.dev/installing/custom-plugins/ . Готовая стандартная установка не подхватывает отдельные userplugins автоматически.
2. Скопировать всю папку `integrations/vencord/majesticWorkspace` в `Vencord/src/userplugins/majesticWorkspace`.
3. В исходной папке Vencord выполнить его штатную сборку и установку: `pnpm build`, затем `pnpm inject`. Перезапустить Discord и включить MajesticWorkspace в настройках плагинов.
4. Настроить облачный процесс по `.env.example`: DISCORD_AUTH_MODE=vencord, DISCORD_INTERVAL_SECONDS=900. DISCORD_TOKEN не нужен. Создать отдельное случайное значение DISCORD_BRIDGE_TOKEN длиной не меньше 32 символов; оно должно отличаться от API_READ_TOKEN/API_WRITE_TOKEN. Это ключ вашего Workspace, не токен аккаунта Discord. Не отправлять ключи в чат и не включать `.env` в архивы.
5. В настройках плагина указать URL Workspace и его DISCORD_BRIDGE_TOKEN. Локальный URL — `http://127.0.0.1:15377`; для Wispbyte нужен публичный HTTPS-адрес. Открыть выбранные серверы в Discord, чтобы клиент загрузил сведения о них.
6. Запустить сервер `npm start`. Для облачной установки сначала выполнить `npm ci` на Node.js 24.18+ (либо поддерживаемой версии из package.json). Плагин обращается к Workspace сам; входящий порт на ПК открывать не нужно.

## MCP

Облачный `/mcp` и локальный majestic_workspace предоставляют:

| Инструмент | Назначение |
|---|---|
| `discord_export({guildId, full:true})` | Полный повторный проход; сразу возвращает ID задания |
| `discord_export({guildId, full:false})` | Продолжение первой загрузки или обновление новых сообщений и закрепов |
| `discord_export_status({guildId})` | Прогресс, доступность клиента, полнота и ошибки |
| `discord_structure({guildId})` / `discord_roles({guildId})` | Структура и роли |
| `discord_information({guildId,channelId,limit,offset})` | Сообщения; продолжать по nextOffset либо beforeId=nextBeforeId |
| `discord_search({guildId,q})` | Поиск по тексту и embeds с прямыми ссылками |
| `discord_message_history({guildId,channelId,messageId})` | Наблюдаемые версии сообщения |

Для локального MCP настроить `.env` в корне проекта: CLOUD_URL (либо PUBLIC_URL), API_READ_TOKEN и API_WRITE_TOKEN. После добавления нового модуля переподключить MCP или открыть новый чат. Значения ключей передаются только заголовками. Плагин имеет отдельный ключ, который не даёт читать базу и запускать публикации форума.

Без HTTP и MCP можно поставить задания командой `node cloud/scripts/discord-request.js`: без аргументов — оба выбранных сервера, `--update` — обновление, `--status` — состояние. Задания сохраняются в SQLite и ждут плагин. Планировщик ставит обновление каждые 900 секунд, не создавая дублей активного задания.

## Что означает полнота

Экспортирует доступную текстовую историю, активные и доступные архивные ветки, роли, права, описания, закрепы, исходный текст, текст embeds, ссылки и метаданные вложений. Личные сообщения и полный список участников не собираются. Двоичные вложения, аудио и видео не скачиваются. Ссылки на файлы Discord могут истекать; обновление сообщения может получить новую ссылку, но это не архив самих файлов.

Начальная загрузка идёт до конца истории, без лимита «последние 100 сообщений». Данные передаются небольшими пакетами; курсор подтверждается только вместе с записью. Повтор одного пакета не создаёт дубль. Закрытие Discord останавливает сбор, но база остаётся доступной. После перезапуска сбор продолжится с подтверждённой страницы.

Правки и удаления сохраняются, когда клиент их получает. Каждые 15 минут обновляются структура, закрепы и новые сообщения. Старые правки/удаления за время офлайна гарантированно сверяются только полным повторным проходом. Историю редакций до первого подключения восстановить нельзя. Кеш Discord не считается полной историей.

`partial`, `failed`, `historyComplete:false` означают незавершённую выгрузку. Перечисление веток или чтение канала может быть запрещено правами; защита не обходится. При лимите SQLite (MAX_DB_MB, по умолчанию 160 МБ) экспорт останавливается с EXPORT_QUOTA и сохраняет уже принятые страницы; старые данные не удаляются молча. Недоступные части перечисляются в статусе. Это консервативная оценка полноты текущего прохода, а не гарантия получения всех исторических событий Discord.

`job` по умолчанию показывает последнее задание, которое может ещё стоять в очереди. `activeJob` отдельно показывает выполняющееся задание и последнюю ошибку принятия пакета. `lastDataAt` — время последнего сохранения данных канала: его следует проверять вместе со счётчиком сообщений. Само `bridgeOnline:true` и время heartbeat не доказывают продвижение выгрузки. После успешного повторного пакета активная ошибка очищается.

`storage` показывает размер файла SQLite (`dbBytes`), настроенную квоту (`maxDbBytes`) и страницы, доступные для повторного использования (`reusableBytes`). Освобождённые страницы используются новыми пакетами; файл на диске при этом не обязан уменьшаться. При реальном `SQLITE_FULL` транзакция может отмениться автоматически: ошибка повторного ROLLBACK больше не скрывает причину, а отвергнутая страница не подтверждается.

В версии со сжатием `storage.bodyEncoding=deflate-v1`, а `compressionMigrated=true` означает окончание преобразования и уплотнения. `quotaRemainingBytes` суммирует свободную часть квоты и повторно используемые страницы. Текущие тела сообщений и прошлых редакций хранятся с Deflate без потерь, когда это уменьшает размер. API декодирует их автоматически, поиск использует прежний текст. Управляющие символы, исходные строки, номера редакций и курсоры сохраняются. Неизменившийся поисковый текст не перезаписывает FTS-индекс.

Первое преобразование выполняется после проверенного backup и до открытия HTTP-порта. После транзакционного сжатия VACUUM уплотняет свободное место внутри страниц; временная база размещается на диске. При сбое уплотнения следующий запуск повторяет его без замены исходного backup. База получает версию 2: для отката требуется восстановить совместимую резервную копию вместе со старыми исходниками. Квота не увеличивается автоматически, и сжатие не является обещанием уместить произвольный объём истории.

Текущая редакция сообщения хранится один раз в `discord_messages`, предыдущие редакции — в `discord_message_versions`. API истории объединяет их с сохранением пагинации и общего лимита HISTORY_VERSIONS. При запуске старой базы приложение сначала создаёт и проверяет резервную копию, даже при BACKUP_COUNT=0, затем удаляет только записи истории, у которых совпадают сообщение, номер редакции, полный текст JSON и время редакции с текущей записью. Реальные предыдущие редакции не удаляются этой миграцией. При ошибке резервного копирования очистка и приём запросов не начинаются. Уже принятое задание и его курсор сохраняются.

Исходный текст сообщений, полей embeds и описаний вложений сохраняется без удаления управляющих символов. ANSI-последовательности и служебные символы удаляются только из поискового индекса. Ограничения типов, размера пакетов и длины полей продолжают действовать; отвергнутый пакет не сдвигает подтверждённый курсор.

Vencord и автоматизация личного аккаунта нарушают условия Discord. Отсутствие токена аккаунта в облаке этот риск не устраняет. Плагин не извлекает токен и не пытается обходить ограничения доступа.

## Проверка

`npm test` проверяет импорт, поисковую базу, подтверждения, восстановление и коллектор на имитации Discord. `npm run check` проверяет JavaScript, синтаксис TypeScript плагина и OpenAPI. Это не заменяет сборку внутри исходников Vencord и пробный экспорт из живого клиента.
