# Сжатие и уплотнение SQLite, 24.11.2026

Подготовлено для уже работающего Majestic Discord Bridge после повторного достижения EXPORT_QUOTA на 65 328 сообщениях. Обработка ошибки SQLite и очистка дублей уже применялись на Wispbyte; новое сжатие и уплотнение проверены локально, но ещё не подтверждены в живой базе.

## Установка на действующий сервер

1. Остановить приложение в панели Wispbyte.
2. В `/home/container/cloud/src` сохранить прежние `store.js`, `discord-bridge.js`, `server.js` и `discord-body.js`, если они существуют, добавив к именам `.pre-compression-20261124.bak`. Если копия с таким именем уже есть, использовать другое свободное имя.
3. Загрузить свежий `Majestic-Discord-Storage-Fix.zip` в корень `/home/container` и распаковать там. В архиве четыре модуля и инструкция `INSTALL.txt`. При обновлении из GitHub использовать актуальный main с новым discord-body.js.
4. Запустить приложение с прежней командой запуска. Настройки Vencord менять и пересобирать плагин не требуется.
5. При первом запуске приложение создаст и проверит резервную копию базы в настроенном DATA_DIR, подпапке `backups`. После проверки оно сожмёт текущие сообщения и предыдущие редакции в одной транзакции, затем уплотнит файл SQLite. До окончания этой операции HTTP-порт не открывается. Текст, история, номера редакций и курсоры сохраняются. Ошибка backup останавливает процесс до преобразования. Неудачное уплотнение повторяется на следующем запуске без замены исходной резервной копии.
6. Проверить `discord_export_status` для обоих выбранных серверов. `storage.bodyEncoding=deflate-v1` и `storage.compressionMigrated=true` подтверждают новую версию и законченное преобразование. `quotaRemainingBytes` учитывает и свободную часть квоты, и повторно используемые страницы. Следить за ростом `messageCount` и изменением `lastDataAt`. `bridgeOnline:true` отдельно не доказывает продвижение.

В архиве нет `.env` и базы. Для действующей установки не запускать первоначальную настройку и не заменять эти данные. При развёртывании из GitHub `dadidkil/mjapi` использовать коммит, содержащий оба исправления INVALID_TEXT и SQLite. Обновление репозитория само по себе не подтверждает установку кода на Wispbyte.

## Что исправлено

- Ошибка заполнения SQLite больше не скрывается повторным ROLLBACK. При достижении квоты страница отклоняется целиком с EXPORT_QUOTA, без сдвига курсора и ложного завершения выгрузки.
- Текущая редакция хранится один раз. API истории возвращает её вместе с сохранёнными предыдущими редакциями и сохраняет пагинацию.
- Полные JSON-тела сообщений и прошлых редакций сжимаются без потерь, когда это экономит место. Старый текстовый формат также читается. Поиск продолжает работать по прежнему тексту, API возвращает обычные сообщения.
- Уплотнение VACUUM собирает свободное место внутри страниц и уменьшает файл. Оно использует временные файлы, сохраняет установленный лимит SQLite и выполняется до открытия HTTP-порта.
- Неизменившиеся сообщения и изменения без правки поискового текста больше не перезаписывают FTS-индекс при повторном проходе.
- Включено прежнее исправление INVALID_TEXT для исходных сообщений с управляющими символами.

Проверка: 85 тестов успешно, 0 ошибок, 1 тест официального SDK MCP пропущен из-за недоступной зависимости; синтаксис 42 файлов и 25 путей OpenAPI. Проверены реальные квоты SQLite, backup, остановка при ошибке в середине преобразования, повтор после неудачного уплотнения, открытие преобразованной базы заново и продолжение записи в пределах прежней квоты.

В живой базе подтверждены 65 328 сообщений первого сервера и 0 второго. Оба первых задания получили EXPORT_QUOTA при квоте 160 МиБ. Повторный полный проход не считается завершённой выгрузкой. Новое сжатие ещё требует проверки на хостинге; итоговая экономия места заранее не обещается. При повторном заполнении нужен отдельный выбор объёма хранения; старые сообщения автоматически не удаляются.

После преобразования используется версия базы 2. Для отката требуется согласованная пара старых исходников и резервной копии до преобразования; прежнее приложение откажется открывать новый формат с DB_VERSION. Существующие .env и база в архив не входят и при обновлении не заменяются.
